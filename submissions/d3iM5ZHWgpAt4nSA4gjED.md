## 项目简介

AIBot 是一个可自行部署的 AI 对话机器人，通过 Bot API 接入兼容 OpenAI `/chat/completions` 规范的模型服务。项目支持流式回复、上下文管理、图片与文档输入、网页搜索、工具调用、多模型切换、群聊自动回复和分级权限管理。

项目使用 Python 开发，Pyrogram 负责消息交互，YAML 保存运行配置，SQLite 保存会话与长期记忆数据。模型、模型 API Bot Token 等凭据均由部署者自行提供。

本次维护主要完成长期记忆闭环，并针对 Js2Py 的 CVE-2024-28397 增加运行时防护；相关代码均集中在 `main.py`，最终版本号为 `1.0.18`。

## 训练营期间的主要增量

统计截止日期为 2026-09-27。最近 7 天内共有 4 个有效提交，均提交于 2026-09-26；以下内容不包含更早的项目功能。

### 长期记忆

新增可配置的长期记忆能力，完整链路如下：

1. 在配置中加入 `AI.Memory.Enable`，用于单独控制长期记忆。
2. 在 SQLite 中创建 `memories` 表，以 `(scope, topic)` 作为联合主键，保存记忆内容及更新时间。
3. 支持 `user:<user_id>` 和 `chat:<chat_id>` 两种作用域，分别保存个人记忆与当前聊天共享记忆。
4. 使用 SQLite UPSERT 写入记忆；相同作用域和主题再次保存时，会更新原有内容而不是创建重复记录。
5. 每次请求模型前读取个人记忆和聊天记忆，并作为额外系统消息加入上下文。
6. 向模型提供 `memory_save` 和 `memory_delete` 工具，使模型可以根据对话保存、更新或删除记忆。
7. 新增 `/memory` 命令，可查看记忆、清空个人记忆；管理员还可清空当前聊天的共享记忆。
8. 普通聊天、Guest Query 和 Chosen Inline Result 三条处理路径均接入记忆读取及工具调用。

同时补充了输入限制：记忆主题最长 100 个字符，内容最长 2000 个字符。该限制用于控制单条数据规模，避免无界内容直接写入数据库和模型上下文。

### 长期记忆优化

初版功能完成后继续进行了调整：

- 将记忆工具从通用的 `AI.Tool.Enable` 开关中解耦，只由 `AI.Memory.Enable` 控制。
- 在 `/stats` 及访客状态信息中显示长期记忆是否启用。
- `/memory` 查询结果不再于 30 秒后自动删除，便于查看和管理。
- 统一 Bot 命令菜单及帮助文本中的记忆功能说明。
- 将项目版本从 `1.0.17` 更新为 `1.0.18`。

针对 CVE-2024-28397 增加启动时运行的 `js2py_monkey_patch()`：包装 `Object.getOwnPropertyNames` 的原实现，并将返回值转换为普通 Python `list`，用于限制现有 Js2Py JavaScript 执行路径中的风险。

### 命令帮助清理

## 实现说明

### 数据结构

长期记忆使用现有的 SQLite 数据库保存，表结构包含：

| 字段 | 用途 |
| --- | --- |
| `scope` | 区分个人记忆或聊天共享记忆 |
| `topic` | 记忆主题，同一作用域内唯一 |
| `content` | 记忆正文 |
| `updated` | 最近更新时间 |

`(scope, topic)` 联合主键同时解决了作用域隔离和同主题覆盖问题。当前实现不依赖额外的向量数据库，部署方式与原项目保持一致。

### 调用流程

```text
用户消息
  -> 根据 user_id / chat_id 读取长期记忆
  -> 将记忆加入模型系统上下文
  -> 模型生成回复，必要时调用 memory_save / memory_delete
  -> SQLite 新增、覆盖或删除对应记录
  -> 后续对话再次读取最新记忆
```

### 权限

- 个人记忆按 用户 ID 隔离。
- 聊天记忆按 Chat ID 共享。
- `/memory clear chat` 仅允许管理员执行。
- 是否启用长期记忆由 `AI.Memory.Enable` 控制。
- `/memory` 面向管理员或已加入 AI 白名单的群组开放。

## 复现与演示

先根据项目 README 完成 Bot、模型提供商及默认模型配置，再确认：

```yaml
AI:
  Memory:
    Enable: true
```

建议按以下顺序演示：

1. 启动 Bot，通过 `/stats` 确认长期记忆状态为启用。
2. 在对话中提供一项适合长期保存的信息，使模型调用 `memory_save`。
3. 使用 `/memory` 查看已保存的个人记忆和聊天记忆。
4. 清理普通对话上下文后再次提问，确认新请求仍会读取长期记忆。
5. 使用 `/memory clear` 清空个人记忆；管理员可使用 `/memory clear chat` 清空当前聊天的共享记忆。
6. 再次执行 `/memory`，确认对应记录已经删除。

> `/memory clear chat` 会删除当前聊天范围内的全部共享记忆，演示前应确认该聊天中的数据可以清理。

## 难点、取舍与学习

### 作用域设计

长期记忆既需要跨会话保留个人信息，也需要支持群聊共享信息。最终使用带前缀的作用域键区分 `user` 和 `chat`，再通过联合主键约束主题。这样无需拆分数据表，也能避免不同用户或群组之间的数据互相覆盖。

### 模型上下文接入

记忆不只是写入数据库，还需要在后续请求中稳定召回。本次将数据库读取、系统消息注入和模型工具调用串成闭环，并同步覆盖普通聊天、访客查询与内联结果，避免功能只在单一入口生效。

### 功能开关解耦

首版中，记忆工具同时依赖通用工具开关与记忆开关。后续提交将两者解耦，使长期记忆可以独立启用，并在状态页明确展示当前配置，减少部署时的排查成本。

### 安全补丁边界

针对第三方依赖漏洞采用 monkey patch 可以快速降低现有执行路径的风险，但会依赖依赖库内部结构。
